## 0. エグゼクティブサマリー（3行）

1. **市場は空白**。「工程プリセット × 複数顧客の掛け持ち × ログ保存」を正面から解いた専用タイマーは事実上存在しない。代替は汎用マルチタイマーか物理タイマーの力技運用。
2. **現状の Salon Pacer は「1人用・単一タイマー」で完成度は高いが、現場の主作業（同時2〜5人の掛け持ち）に乗れていない**。ここが普及の天井。
3. **勝ち筋は2つのキラー機能**：「掛け持ちダッシュボード（複数タイマー並行＋手が空く順）」と「見逃さない通知（終了＋事前アラート）」。ただし**その前提として、いま最大の摩擦である『設定の大変さ』を再設計で潰す**ことが最優先。設定が全機能の入口だから。

## 2. なぜ「全員が使う」に届かないか — 4つの壁

| 壁 | 内容 | 根拠 |
|---|---|---|
| **設定の壁（最優先）** | テンプレが縮毛矯正1本だけ。他メニューは12工程ゼロ入力。並べ替え▲▼連打、複製不可、終了予定時刻が設定段階で出ない。初回はいきなり編集画面で「何をどうすれば」が不明 | 調査4 |
| **掛け持ちの壁** | 現場は1人専任ではない。同時2〜5人が標準。5人掛け持ちで1人あたり実働約24分。今のアプリは1人専用で主作業に乗らない | 調査3（2時間で5人＝24分/人）、調査1（物理 Triple Color Timer が「3人同時」を製品コンセプト化） |
| **チラ見の壁** | 手がふさがり画面を凝視できない。見ていない間に放置時間超過＝クレーム・損害賠償リスク。カラーは約30分が発色限度 | 調査3（放置クレーム/損害賠償）、調査5（iOSバックグラウンド制約） |
| **習慣化の壁** | 1人用の閉じたツールは飽きる/忘れる。全国普及には人から人へ広がる仕組み（テンプレ共有）が要る | 調査6 |

**「工程シーケンス × 掛け持ち1画面俯瞰 × ログ」を満たす製品はゼロ。**

| マルチタイマー(LemonClip) | 汎用マルチタイマー | △ 同時可 | △ カテゴリのみ | × | 美容文脈なし |
| 山野タイマー | 美容師試験向け単機能 | × | × | × | 評価2.8、不具合報告 |
| PSA+ | サロン管理＋カラー処方 | △ ダブルブッキング扱うがタイマー非主役 | ○ 処方に処理時間（シーケンスでない） | ○ 処方 | 放置時間運用は手薄 |
| Salon Formulator / Charm | 処方・カルテ | × | ○ 処方記録（時間管理弱い） | ○ | タイマー非主眼 |

| SALONBOARD等 予約/POS | 予約・顧客・会計 | △ 予約枠は押さえる | × 枠の内部は管理対象外 | ○予約/会計 | **共存対象。枠の中身は空白** |

**戦略的含意**：Salon Pacer は予約/POS（SALONBOARD等）と競合せず、**「予約枠の内部＝施術が始まってから終わるまでの、複数客分の工程進行管理」という未充足領域に特化**する。差別化軸は ①工程シーケンスのプリセット ②掛け持ち1画面俯瞰 ③ログ保存 の3点。

> 補足（薬機法）：1人にカラーとパーマを同時施術は基本不可。だが**別々の顧客を時間差で掛け持ち**するのは現場の常態で、ここがタイマー需要の本丸。

## 4. 【最優先章】設定 UX 再設計

> 設計思想：**「ゼロから作らせない。選んで始める → 微調整する」**。施術中の片手・濡れ手でも使える大きなタップ領域（44px以上）。
> これを最優先に置く理由：掛け持ちも通知も、ユーザーが**自分のメニューを設定し終えて初めて使える**。設定が重い限り、その先のキラー機能まで到達しない。

### 現状の問題点（影響度順）

- **A. 既製テンプレが縮毛矯正1本だけ** — 他メニューは12工程ゼロ入力。`presets` 初期値が空でプリセット・ファーストの入口が無い（最大の問題）。
- **B. 分数入力がボタン連打地獄** — 30→45分にするのに `+5`×3 or `+`×15。よく使う値へのワンタップが無い。
- **C. 並べ替えが▲▼で1段ずつ** — 12番目→2番目で▲を10回。
- **D. 工程「複製」が無い** — 「シャンプー」が3回出るのに毎回打ち直し。
- **E. プリセットのメンタルモデルが弱い** — 「いま編集中はどのプリセットか」表示なし。上書き保存不可（常に新規）。
- **F. 合計が数字止まり・妥当性チェック無し** — 設定段階で終了予定時刻が出ない。0分工程も保存できる。
- **G. オンボーディング皆無** — 初回いきなり編集画面。`TotalDuration` が2回描画（重複コード）。
- **H. データ構造の制約** — `Step.id:number` を `Math.max+1` 採番で衝突しうる。`Preset` に category/icon が無くギャラリー化できない。

### 提案1: テンプレ・ファースト / テンプレギャラリー（難易度: 中）

設定を開いた最初の画面を「テンプレ選択」にする。`constants.ts` に既製テンプレを複数同梱。

```

│  メニューを選ぶ                      ✕  │
├─────────────────────────────────────────┤
│  おすすめテンプレ                        │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ │
│  │  💧       │ │  🎨       │ │  🌀      │ │
│  │ 縮毛矯正  │ │ カラー    │ │ パーマ   │ │
│  │ 約3時間40 │ │ 約1時間50 │ │ 約2時間  │ │
│  │ 12工程    │ │ 7工程     │ │ 9工程    │ │
│  │ [選択]    │ │ [選択]    │ │ [選択]   │ │
│  └──────────┘ └──────────┘ └──────────┘ │
│  ┌──────────┐ ┌──────────┐               │
│  │ ✨ﾄﾘｰﾄﾒﾝﾄ │ │ ＋ 空から │               │
│  └──────────┘ └──────────┘               │
│  マイプリセット                          │

- カードに**所要時間・工程数を事前表示**（選ぶ前に判断できる）。タップで即「編集できる状態」へ。
- 「マイプリセット」は従来のユーザー保存分。`⋯` メニューに 読込/複製/名前変更/削除 を集約し誤タップ防止。

### 提案2: 工程編集の刷新（難易度: 中〜大）

```

│ ← テンプレ   縮毛矯正(編集中)        ✕  │
├─────────────────────────────────────────┤
│  終了予定 18:42 ／ 合計 3:40 ／ 12工程   │ ← 常時固定ヘッダ
├─────────────────────────────────────────┤

│ ⠿ 2 シャンプー                  10分  ⋯ │ ← 行タップで時間ピッカー
│ ⠿ 3 準備・薬剤塗布              20分  ⋯ │
│ ⠿ 4 薬剤放置                    30分  ⋯ │
│   ┌─────────────────────────────────┐   │
│   │ 「薬剤放置」 時間を選ぶ          │   │ ← 行タップで展開
│   │ [5][10][15][20][30][45][60] 分  │   │ ← よく使う値ワンタップ

│   │ [複製] [削除]                    │   │
│   └─────────────────────────────────┘   │

| 現状 | 再設計 | 根拠 |
|---|---|---|
| 並べ替え▲▼1段ずつ | **D&D並べ替え**（`@dnd-kit/sortable`）。▲▼は`⋯`内に補助で残しアクセシビリティ確保 | 調査2（HIIT系の業界標準） |
| 複製なし | 各工程に**複製ボタン**（同種工程＋分数を直下に即挿入） | 調査2（Seconds の copy/paste） |
| 追加は常に空の新規10分 | 追加時に**直前工程の分数をプリフィル**＋「よく使う工程から追加」チップ | 調査2/4（スマートデフォルト） |
| −/＋/+5連打 | **よく使う値チップ（5/10/15/20/30/45/60分）＋微調整−/＋＋直接入力**。長押し連続増減 | 調査2（NN/g ステッパー指針） |
| 累積時刻が見えない | 各カードに「開始◯分〜」累積バッジ | 調査2（即時フィードバック） |
| 削除は即🗑️ | スワイプ削除＋アンドゥ・トースト | 調査2 |

### 提案3: 合計時間のリアルタイム表示＆妥当性チェック（難易度: 小〜中）

- `TotalDuration` を**固定ヘッダに常駐化**し、現状の **2回描画（重複コード）を解消**。
- **終了予定時刻（now + 合計）を HH:mm 表示** — サロンで最も欲しい情報。
- 妥当性（boundary で fail-fast）：`durationMinutes <= 0` は警告＋保存ブロック、工程0件は開始無効、極端な合計（30分未満/6時間超）はやわらかい注意（ブロックしない）。

### 提案4: 初回オンボーディング（難易度: 小）

初回のみ（localStorage フラグ）テンプレギャラリーを全画面で前面に。「選ぶ→確認→開始」3ステップ以内。説明1行「あとで自由に調整OK」で不安を消す。

### 提案5: データ構造（後方互換／難易度: 小〜中）

すべて**任意プロパティ追加**で既存 localStorage を壊さない。

```typescript
export type StepCategory =
  | 'counseling' | 'shampoo' | 'apply' | 'process'
  | 'dry' | 'iron' | 'treatment' | 'finish' | 'other';

export type Step = {
  id: string;            // 変更: number → string(uuid)。衝突回避・複製/配布に安全（影響大のため後回し可）
  name: string;
  durationMinutes: number;
  category?: StepCategory; // 追加(任意): チップ候補・アイコン表示用
};

export type Preset = {
  id: string;
  name: string;
  steps: Step[];
  icon?: string;          // 追加(任意): '💧'等
  category?: string;      // 追加(任意): フィルタ用
  isTemplate?: boolean;   // 追加(任意): 同梱テンプレ vs ユーザー保存
  createdAt?: number;     // 追加(任意)
};
```

```typescript
// constants.ts
export const STEP_PRESET_NAMES = ['カウンセリング','シャンプー','薬剤塗布','薬剤放置','中間処理','ドライヤー','アイロン','２液','仕上げ・撮影'];
export const QUICK_DURATIONS = [5, 10, 15, 20, 30, 45, 60];
export const TEMPLATES: Preset[] = [
  { id: 'tpl-straightening', name: '縮毛矯正', icon: '💧', isTemplate: true, steps: SCHEDULE_STEPS },
  { id: 'tpl-color',  name: 'カラー', icon: '🎨', isTemplate: true, steps: [/* 7工程 */] },
  { id: 'tpl-perm',   name: 'パーマ', icon: '🌀', isTemplate: true, steps: [/* 9工程 */] },
];
```

- `Step.id` の `number → string` 変更は影響範囲が広い（`StepRecord.stepId` 等）。**ロード時に `migrateSteps()` を挟む**。難易度を抑えるなら id 変更は見送り、`category`/`icon` 追加のみで提案1〜4は実現可能（堅実ルート）。
- 同梱テンプレは `constants.ts` の `TEMPLATES`（`isTemplate:true`）として定義し、`useSettings` で `presets`（ユーザー保存分）と別配列で合流表示。
- 複製/任意移動は immutable（spread）で実装（`coding-style.md` 遵守）。

## 9. 【新・最優先】施術中の工程編集を安全に実装する

> 4エージェントで実コード（`timerReducer.ts`/`useTimer.ts`/`useSettings.ts`/`useProgressCalculation.ts`/`types.ts` 等）を解析し統合した安全設計。
> 背景：実際の施術は即興（「ここでカット入れよう」等、やりながら工程が変わる）。固定シーケンスは**練習**には良いが**本番**では使いづらい。だが自由に変えすぎると「予定 vs 実績」のペース把握が壊れる。両立が設計の急所。

### 9-0. 根本原因（すべての不具合の源）

1. **進行位置が配列インデックス（`currentStepIndex`）で管理**。id でなく位置で追うため、`steps` 編集で「現在地」が別工程にズレる。
2. **`steps`（useSettings）と `TimerState`（useTimer）が別ストアで、ワーキングコピーが無い**。設定編集が進行中タイマーに即反映。当初予定のスナップショットも無い。
3. **「予定 vs 実績」が常に現在の `steps` から都度再計算**（`slice(0, currentStepIndex)` 等の位置依存）。実績の真実源 `completedSteps` と二重管理。

### 9-1. リスク台帳（18件）

深刻度 HIGH > MEDIUM > LOW。

| # | 不具合 | 深刻度 | 防ぎ方 |
|---|--------|--------|--------|
| R1 | 現在地より前への挿入/削除で `currentStepIndex` がズレ進行中工程がワープ | HIGH | 進行位置の id 基準化、または `index > currentStepIndex` のみ許可 |
| R2 | 現在実行中の工程を削除/スキップで `currentStep` が undefined → 施術中に完了画面へ | HIGH | スキップを3ケース分岐。MVPは現在工程スキップを対象外 |
| R3 | 完了済みと未実施の境界が並べ替えで破壊 | HIGH | 施術中は完了済み・現在工程を編集ロック。並べ替えは未実施同士のみ |
| R4 | 工程が変わっても `stepStartTime`/音声フラグ未リセット → 経過誤り・終了音誤発火 | HIGH | 現在工程が変わる編集で `stepStartTime` 再設定・音声フラグ reset |
| R5 | 工程名が id 解決依存で、削除→追加やプリセット読込で履歴に別名が焼き込まれる | HIGH | `StepRecord.stepName?` を追加し記録時にスナップショット |
| R6 | 進捗バー幅・%・完了予定が編集の瞬間に不連続ジャンプ | MED | START 時に当初総予定をスナップショットし分母固定 |
| R7 | スケジュール進捗% が分母変化で跳ねる/逆戻り | MED | R6 と同じく当初総予定で分母固定 |
| R8 | 並べ替えで完了予定時間（slice依存）が乖離しステータス色を誤判定 | HIGH | 完了予定は `completedSteps[].plannedDuration` から積む。slice 排除 |
| R9 | 挿入で分母が増え、同じ遅延でも「順調」に化ける | HIGH | 本番=変更後予定で判定／練習=当初予定で判定（当初予定を保持） |
| R10 | `previousStep` の時刻復元が編集後に破綻 | MED | record と工程を stepId 突合、不一致は now 起点フォールバック。MVPは workingSteps 固定で回避 |
| R11 | スキップ工程の `actualDuration` 未記録で総経過と実績和が乖離 | MED | スキップ時に進行中工程を `actualDuration=stepElapsedSeconds` で1件記録 |
| R12 | stale 復元後に `currentStepIndex` が範囲外 → 即完了/操作不能 | MED | `loadTimerState(key, steps)` に変更し index クランプ+id 存在検証 |
| R13 | 一時停止中の編集で `totalPausedMs` 会計が壊れ経過が負値 | MED | 編集UIで自動 PAUSE/RESUME（MVP採用） |
| R14 | `durationMinutes=0` で `progressRatio` が Infinity/NaN | HIGH | `>=1` の境界検証＋`planned>0 ? ... : 0` ガード |
| R15 | `stepWidths` の 0除算ガード漏れで全工程削除時に NaN 伝播 | MED | `totalDurationSeconds>0 ? ... : 0`。0工程は START 前にブロック |
| R16 | 0件で START すると即完了画面 | MED | 開始ボタン非活性 |
| R17 | 重複保存ガードが時刻のみで連続2件目を無言破棄 | LOW | 内容ハッシュ併用（当面は認識のみ） |
| R18 | 24h stale 判定が startTime 基準で長時間施術を誤 stale 化 | LOW | `lastInteractionAt` 基準に |

### 9-2. 安全な目標アーキテクチャ

- **「保存予定」と「今日のワーキングコピー」を分離**：START 時に `steps` をディープコピーして `TimerState.workingSteps` に固定。タイマー・進捗・音声・完了判定はすべて `workingSteps` 参照。設定画面の編集が進行中セッションを壊さなくなる（R3/R5/R10 を一掃）。
- **編集は「これからの工程（future）」のみ**：past・current は編集ロック。挿入は「末尾」か「現在位置の直後」に限定（`index > currentStepIndex`）。
- **StepRecord のスナップショット化**：`stepName?` を optional 追加し記録時に焼き込む。表示は `record.stepName ?? find ?? '工程N'`。
- **id 衝突回避**：恒久的には進行位置を id 基準（`currentStepId`）で持ち描画時に `findIndex` で解決。
- **当初予定の保持**：START 時に `originalTotalPlannedSeconds`/`mode` をスナップショット。進捗・完了予定・遅延判定の分母を baseline 固定。
- **足す reducer アクション**：`START` 拡張（workingSteps/baseline/mode）、`INSERT_FUTURE_STEP`、`SKIP_FUTURE_STEP`、（恒久）`SKIP_CURRENT_STEP`/`REORDER_PENDING`。全編集で `isPaused` ガード。

**不変条件（INVARIANTS）**：①実施中工程の同一性保持 ②`completedSteps` 不可侵 ③`completedSteps.length === currentStepIndex` ④`0 <= currentStepIndex <= workingSteps.length` ⑤id 参照整合 ⑥時間単調（≥0） ⑦工程変化で音声フラグ reset ⑧baseline 不変。

### 9-3. 最小MVPスコープ

**「これからの工程に1つ挿入」＋「これからの工程をスキップ」のみ。** 並べ替え・現在/過去編集・練習採点UI・多段Undoは対象外（YAGNI）。

MVP必須ガード：①挿入/スキップは `index > currentStepIndex` のみ（index補正不要で安全）②workingSteps 固定 ③0件 START 防止 ④編集UIで自動 PAUSE→RESUME ⑤直後5秒の「元に戻す」トースト ⑥`durationMinutes>=1` 検証と 0除算ガード。

**変更ファイル**：`types.ts`（TimerState に `workingSteps?`/`originalTotalPlannedSeconds?`/`mode?`/`currentStepId?`、StepRecord に `stepName?` を optional 追加）/ `timerReducer.ts`（START 拡張＋2アクション＋`loadTimerState(key, steps)`）/ `useTimer.ts`（workingSteps スナップショット＆参照切替、nextStep で stepName 記録、編集アクション、0件ガード）/ `useSettings.ts`（durationMinutes 下限検証）/ `useProgressCalculation.ts`（0除算ガード・完了予定を completedSteps ベース・分母 baseline 固定）/ `ActiveTimerView.tsx`（挿入/スキップUI・自動PAUSE/RESUME・Undo）/ `CurrentStepControl.tsx`（progressRatio ガード）/ `App.tsx`（0件で開始ボタン非活性）。

### 9-4. 練習モード / 本番モード

| 項目 | 本番（デフォルト） | 練習 |
|------|--------------------|------|
| 編集 | 自由（挿入/スキップ/並べ替え/時間変更） | 全禁止（予定ロック） |
| 判定基準 | 変更後の予定 | 当初予定（固定） |
| 目的 | 現場の柔軟運用 | ズレ採点・トレーニング |
| 状態 | `mode='live'` | `mode='practice'` |

- モードは **START 時に確定**（施術中の切替は採点基準を壊すため不可）。
- MVP では `mode` の器（state＋既定 'live'）だけ用意し、練習採点UIは作らない。

### 9-5. テスト項目（要点）

- `START`：workingSteps が steps のディープコピーで固定（元 steps 変更後も不変）。`mode='live'`/baseline セット。施術中の `START` は no-op。
- `INSERT_FUTURE_STEP`：`index > currentStepIndex` で挿入、`currentStepIndex`/`completedSteps` 不変。`index <= currentStepIndex` は拒否。
- `SKIP_FUTURE_STEP`：future 除去後も `currentStepIndex`/`completedSteps` 不変・実績未計上。残り0で `finishReason='skipped'`。
- `nextStep`：`newRecord.stepName` に現在工程名が焼き込まれる。
- `loadTimerState`：範囲外 index はクランプ、id 不在は stale/フォールバック、workingSteps 不在の旧データでクラッシュしない（後方互換）。
- `useProgressCalculation`：`steps=[]`/`durationMinutes=0` で NaN/Infinity を返さない。完了予定が completedSteps ベース。挿入で分母が当初予定のまま不変。
- 結合：施術中に設定で add/remove/move しても進行中の現在工程・残り・進捗が不変（workingSteps 固定）。0件で開始非活性。編集UIで PAUSE/RESUME。Undo で復元。
- カバレッジ：reducer/計算ロジック 80%+（編集境界・0件・最終工程・loadTimerState 分岐を必須）。

### 9-6. 段階導入の推奨順

1. **第1波（最大効果・後方互換）**：workingSteps 固定（R1/R3/R5/R10）＋ `StepRecord.stepName` スナップショット（R5）。optional 追加のみで既存データ非破壊。
2. **第2波**：baseline 固定（R6/R7/R9）＋完了予定を completedSteps ベース（R8）＋0除算/下限検証（R14/R15）＋0件 START ガード（R16）。
3. **第3波（MVP編集機能）**：`INSERT_FUTURE_STEP`/`SKIP_FUTURE_STEP`＋編集UI＋自動 PAUSE/RESUME＋Undo トースト。
4. **第4波（恒久）**：id 基準進行（currentStepId）、現在工程スキップ、並べ替え、練習採点、loadTimerState 検証強化（R2/R10/R12/R18）。

> **要点**：第1波（workingSteps 固定＋名前スナップショット）だけで HIGH リスクの大半（R1/R3/R5/R10）が消え、しかも optional 追加のみで既存ユーザーのデータを壊さない。編集機能（第3波）の前に第1〜2波で土台を固めるのが安全。
